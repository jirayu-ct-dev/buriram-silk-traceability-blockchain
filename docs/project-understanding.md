# สรุปความเข้าใจโครงงาน Blockchain Architecture Blueprint

เอกสารนี้สรุปข้อกำหนดและแนวทางสำหรับโครงงานหัวข้อ **ระบบตรวจสอบและรับรองแหล่งที่มาของผ้าไหมทอมือบุรีรัมย์ด้วยเทคโนโลยีบล็อกเชน** โดยอ้างอิงเอกสารหลัก `docs/blockchain_project_brief.pdf` ครบทั้ง 19 หน้า

> **Source of Truth:** ข้อความที่ระบุว่าเป็นข้อกำหนดมาจาก `blockchain_project_brief.pdf` ส่วนข้อเสนอเชิงออกแบบสำหรับหัวข้อผ้าไหมจะแยกกำกับไว้อย่างชัดเจน และไม่ถือเป็น Requirement ของอาจารย์จนกว่าจะได้รับการยืนยัน

## Project Understanding

โครงงานนี้เป็นงานกลุ่มสำหรับรายวิชา `4124301 เทคโนโลยีบล็อกเชนและการเข้ารหัสลับ` มีเป้าหมายให้นักศึกษานำความรู้สัปดาห์ที่ 1–12 มาวิเคราะห์ปัญหาท้องถิ่นจังหวัดบุรีรัมย์และออกแบบแนวทางแก้ปัญหาเชิงสถาปัตยกรรม

เอกสาร PDF กำหนดให้การประเมินหลักอยู่ที่ **Blockchain Architecture Blueprint** และไม่ได้บังคับให้พัฒนา DApp อย่างไรก็ตาม จากคำชี้แจงเพิ่มเติมของอาจารย์ที่ทีมได้รับ การทำเว็บสาธิตที่ใช้งานได้มีโอกาสได้รับคะแนนเพิ่ม ทีมจึงกำหนดให้ **เว็บด้วย Nuxt เป็น Implementation Scope ของโครงงาน** ควบคู่กับรายงานและ Blueprint

สิ่งที่อาจารย์ต้องการประเมิน ได้แก่

- เข้าใจว่าเมื่อใดควรใช้ Blockchain
- พิสูจน์ได้ว่าโจทย์มีปัญหาด้านความไว้วางใจหรือการแบ่งปันข้อมูลที่ระบบรวมศูนย์อาจตอบโจทย์ไม่พอ
- เลือก Blockchain Type และ Consensus ให้ตรงกับ Stakeholders จำนวนโหนด และ Trust Model
- เชื่อมโยง Block, Hash, Consensus และ Smart Contract เข้ากับกรณีใช้งานจริง
- พิจารณาความเป็นไปได้ กฎหมาย จริยธรรม ต้นทุน และข้อจำกัด
- สื่อสารและทำงานเป็นทีมอย่างสมดุล

ข้อมูลภาพรวมของโครงงาน:

- กลุ่มละ 4–5 คน
- ดำเนินงานสัปดาห์ที่ 13–16
- คะแนนรวม 20% ของรายวิชา
- การให้คำปรึกษาและร่างรายงาน 5%
- การนำเสนอและรายงานฉบับสมบูรณ์ 15%
- รายงาน 10–15 หน้า
- นำเสนอ 15–20 นาที
- ตอบคำถามเพิ่มเติม 5 นาที
- หัวข้อผ้าไหมเป็นโจทย์ระดับกลาง `★★☆`

ชื่อหัวข้อในรายการทางการคือ **ระบบใบรับรองดิจิทัลผ้าไหมทอมือบุรีรัมย์** ส่วนชื่อที่ใช้กับ repository คือ **ระบบตรวจสอบและรับรองแหล่งที่มาของผ้าไหมทอมือบุรีรัมย์ด้วยเทคโนโลยีบล็อกเชน** ทั้งสองชื่อสามารถออกแบบให้สอดคล้องกันได้ แต่ชื่อหลังไม่ควรถูกตีความให้เป็นระบบ Supply Chain ขนาดใหญ่โดยอัตโนมัติ ควรยืนยันชื่อสุดท้ายกับอาจารย์หากจะใช้ชื่อที่แตกต่างจากรายการทางการ

## Technical Requirements

### System Architecture

ตามเอกสาร ต้องมี System Architecture Diagram ที่แสดงองค์ประกอบของระบบอย่างเป็นเหตุเป็นผล

ข้อเสนอเชิงออกแบบสำหรับหัวข้อผ้าไหม: แผนภาพควรแสดงอย่างน้อย

- Stakeholder แต่ละกลุ่ม
- จุดที่ผู้ใช้ส่ง Transaction
- Application หรือ Interface เชิงแนวคิด
- Blockchain Network
- Validator Nodes
- Smart Contract หรือ Business Rules
- การจัดเก็บข้อมูล On-chain/Off-chain หากมี
- QR Code หรือกลไกตรวจสอบใบรับรอง หากเลือกใช้

เอกสารไม่ได้บังคับให้กำหนดผลิตภัณฑ์ Blockchain จริง เช่น Ethereum, Hyperledger Fabric หรือ Quorum

### Blockchain Type

ต้องเลือกหนึ่งประเภท:

- Public
- Private
- Consortium

ต้องอธิบายโดยเชื่อมโยงกับ:

- ใครมีสิทธิ์เขียนข้อมูล
- ใครตรวจสอบข้อมูล
- ใครควบคุมโหนด
- Stakeholders เชื่อใจกันระดับใด
- มีองค์กรกลางที่ทุกฝ่ายยอมรับหรือไม่

### Consensus

ต้องเลือกจาก:

- PoW
- PoS
- PoA
- PBFT

เหตุผลต้องเชื่อมกับ:

- จำนวน Validator
- ผู้ดำเนินการ Validator เป็นใคร
- โหนดเป็นผู้เข้าร่วมที่รู้ตัวตนหรือไม่
- ต้องทนต่อพฤติกรรมไม่ซื่อสัตย์ระดับใด
- ต้นทุนและความซับซ้อนเหมาะกับโครงงานหรือไม่

### Block Structure

เอกสารระบุให้มี:

- Index
- Timestamp
- Data Fields พร้อมอธิบายว่าเก็บอะไร
- Nonce
- Hash
- Previous Hash

ข้อสังเกตเชิงเทคนิค: `Nonce` อาจมีความหมายต่างกันตาม Consensus หากไม่ได้เลือก PoW ไม่ควรอธิบายว่า Nonce ใช้ขุดเหมืองโดยไม่มีเหตุผล ควรระบุความหมายของฟิลด์ในแบบจำลองให้สอดคล้องกับระบบ หรือขอคำยืนยันจากอาจารย์ว่าต้องการโครงสร้าง Block เชิงการสอนแบบทั่วไปหรือโครงสร้างที่ตรงกับ Consensus ที่เลือก

### Transaction Flow

ตามเอกสาร ต้องแสดงลำดับตั้งแต่เริ่มส่งคำขอจนถึงบันทึกลง Blockchain

ข้อเสนอเชิงออกแบบ: Flow ควรครอบคลุม

1. Actor เริ่มส่งคำขอ
2. ระบบตรวจสิทธิ์และเงื่อนไข
3. Transaction ถูกลงนามหรือส่งเข้าสู่เครือข่าย
4. Validator ตรวจสอบ
5. Consensus รับรอง
6. Transaction ถูกบันทึกลง Block
7. สถานะหรือผลลัพธ์ถูกส่งกลับ
8. ผู้ตรวจสอบภายนอกเรียกดูหลักฐานได้

### Smart Contract Logic

ต้องเป็น Pseudo-code เท่านั้น โดยควรมี:

- ผู้เรียกที่ได้รับอนุญาต
- เงื่อนไข `if/then`
- การตรวจสถานะเดิม
- การเปลี่ยนสถานะ
- ผลลัพธ์สำเร็จหรือปฏิเสธ
- Event หรือ Audit Record หากจำเป็น

ส่วนเว็บ Nuxt เป็นขอบเขต Implementation เพิ่มเติมของทีม ขณะที่รายงานยังต้องแสดง Smart Contract Logic เป็น Pseudo-code ตามข้อกำหนด

## Rubric / Scoring Strategy

| มิติ | น้ำหนัก | แนวทางสู่ระดับสูงสุด |
|---|---:|---|
| ความสมเหตุสมผลของการใช้ Blockchain | 20% | เปรียบเทียบกับ SQL อย่างเป็นธรรม ระบุปัญหาความไว้วางใจ การแก้ไขย้อนหลัง และการแบ่งปันข้อมูลข้ามองค์กร แล้วเลือก Blockchain Type/Consensus จาก Trust Model |
| ความคิดสร้างสรรค์เชิงนวัตกรรม | 20% | ใช้ปัญหาและบริบทผ้าไหมบุรีรัมย์จริง ไม่คัดลอกระบบต่างประเทศ และปรับแนวคิดให้เหมาะกับช่างทอ สหกรณ์ และร้านค้า |
| ความเข้าใจเชิงเทคนิค | 20% | เชื่อม Block, Hash, Previous Hash, Consensus และ Smart Contract เข้ากับ Transaction ผ้าไหมทุกจุด ไม่อธิบายเฉพาะทฤษฎี |
| Evidence-based และการอ้างอิง | 15% | ใช้ APA 7 อย่างน้อย 8 แหล่ง มี Primary Sources อย่างน้อย 3 แหล่ง และใช้แหล่งจริงสนับสนุน Problem Statement และการตัดสินใจเชิงเทคนิค |
| การนำเสนอและตอบคำถาม | 15% | มีโครงเรื่องตั้งแต่ปัญหา เหตุผลใช้ Blockchain Architecture และความเสี่ยง สมาชิกทุกคนพูด และเตรียมตอบคำถามเชิงลึก |
| การทำงานเป็นทีม | 10% | แบ่งงานสมดุล มีหลักฐานการมีส่วนร่วม ทุกคนเข้าใจภาพรวม ไม่ใช่เฉพาะส่วนของตัวเอง และผล Peer Evaluation สม่ำเสมอ |

### กลยุทธ์สำคัญสำหรับคะแนนสูงสุด

- เริ่มจากปัญหา ไม่ใช่เริ่มจากความต้องการใช้ Blockchain
- ไม่อ้างเพียงว่า Blockchain ปลอดภัย โปร่งใส หรือทันสมัยกว่า
- ต้องตอบได้ว่า หากใช้ MySQL/PostgreSQL แทนจะเกิดปัญหาอะไร
- การเลือก Consortium ร่วมกับ PoA หรือ PBFT จะเหมาะสมต่อเมื่อ Trust Model รองรับ
- Diagram, Block Structure, Transaction Flow และ Pseudo-code ต้องเล่าระบบเดียวกันและใช้ชื่อ Actor/สถานะตรงกัน
- ต้องอธิบาย Block, Hash, Consensus และ Smart Contract โดยเชื่อมกับ Use Case ไม่ใช่อธิบายทฤษฎีทั่วไป
- ต้องยอมรับข้อจำกัดของ Blockchain อย่างตรงไปตรงมา
- ใช้หลักฐานที่น่าเชื่อถือสนับสนุนทั้งปัญหาและการตัดสินใจเชิงเทคนิค
- ทุกคนในกลุ่มต้องมีส่วนร่วมพูดและตอบคำถามได้

เอกสารให้คำอธิบายเฉพาะระดับ 4 และระดับ 2 ยังไม่พบเกณฑ์รายละเอียดสำหรับระดับ 3 และระดับ 1 หรือสูตรแปลงคะแนนย่อยเป็นคะแนนรวม

- Scope ต้องทำได้ภายในช่วงค้นคว้าและออกแบบประมาณ 2 สัปดาห์
- ต้องผูกกับบริบทจังหวัดบุรีรัมย์
- ต้องใช้ข้อมูลจริงสำหรับ Problem Statement
- ต้องมี Stakeholders 3–5 กลุ่ม
- ห้ามใช้ Blockchain กับโจทย์ที่ SQL ก็เพียงพอโดยไม่มีเหตุผล
- ห้ามคัดลอก Whitepaper หรือบทความ
- ห้ามใช้ Wikipedia เป็นแหล่งอ้างอิงหลัก
- ไม่ควรให้สมาชิกเพียง 1–2 คนทำงานหลัก

### ข้อเสนอเพื่อควบคุม Scope

- พัฒนาเฉพาะเว็บ Nuxt ที่สาธิต Flow หลักได้จริง ไม่มี Mobile Application แยกต่างหาก
- ใช้ PostgreSQL เก็บผู้ใช้ Workflow ข้อมูลส่วนบุคคล และข้อมูลสำหรับแสดงผล
- จำลอง Blockchain ภายในเว็บ/เครื่องด้วย Hash Chain แบบ Append-only และระบุชัดว่าไม่ใช่เครือข่าย Distributed Blockchain จริง
- ไม่ควรเพิ่ม Token, Cryptocurrency หรือ NFT หากไม่จำเป็น เพราะจะเพิ่มทั้ง Scope และประเด็นกฎหมายสินทรัพย์ดิจิทัล
- ไม่ควรออกแบบ Marketplace, ระบบชำระเงิน หรือ Supply Chain ครบวงจร หากไม่จำเป็นต่อปัญหาหลัก
- ควรจำกัด Blueprint อยู่ที่การออกใบรับรอง การบันทึกประวัติที่จำเป็น และการตรวจสอบย้อนกลับ

### สิ่งที่ยังไม่พบในเอกสาร

- รูปแบบไฟล์ที่ต้องส่ง เช่น PDF หรือ DOCX
- ระบบหรือช่องทางอัปโหลด
- วันและเวลาส่งแบบปฏิทิน
- รูปแบบฟอนต์ ระยะขอบ และ Spacing
- จำนวนสไลด์
- รายละเอียดว่า 10–15 หน้ารวมปก สารบัญ และ References หรือไม่
- Blockchain Platform ที่ต้องใช้
- จำนวนโหนดที่กำหนดตายตัว
- Consensus ที่บังคับสำหรับหัวข้อผ้าไหม
- Requirement ให้ทำ Prototype หรือ UI Mockup ไม่ปรากฏใน PDF แต่ทีมได้รับคำชี้แจงจากอาจารย์ว่าเว็บที่ทำงานได้อาจช่วยเพิ่มคะแนน
- นโยบายการใช้ Generative AI
- หลักฐานยืนยันว่าปัญหาปลอมแปลงผ้าไหมเกิดขึ้นในรูปแบบใดหรือรุนแรงเพียงใด
- องค์กรใดเป็นผู้รับรองผ้าไหมอย่างเป็นทางการในระบบที่เสนอ

## Risks / Common Mistakes

- อ้างว่าผ้าไหมปลอมเป็นปัญหาใหญ่โดยไม่มีหลักฐาน
- สรุปว่า SQL ไม่ปลอดภัยหรือแก้ไขข้อมูลไม่ได้ ซึ่งไม่ถูกต้อง
- ไม่ยอมรับว่า Centralized Database อาจเหมาะกว่า หากทุกฝ่ายเชื่อถือสหกรณ์เดียวกัน
- ออกแบบระบบตั้งแต่การเลี้ยงไหม ปลูกหม่อน สาวไหม ย้อม ทอ ขนส่ง ขาย ส่งออก และ NFT พร้อมกัน
- สับสนระหว่างใบรับรองดิจิทัลกับสินทรัพย์ดิจิทัลหรือ NFT
- เก็บชื่อ เบอร์โทร ที่อยู่ หรือเอกสารส่วนบุคคลบน Blockchain โดยตรง
- เชื่อว่า Blockchain รับประกันว่าสินค้าจริงตรงกับข้อมูลที่กรอก ทั้งที่ยังมี Oracle/Garbage-in-garbage-out Problem
- ใช้ QR Code แล้วสรุปว่าป้องกันของปลอมได้ทั้งหมด ทั้งที่ QR สามารถถูกคัดลอกได้
- เลือก PoW สำหรับเครือข่ายเล็กโดยไม่อธิบายต้นทุน
- เลือก PBFT โดยไม่ระบุจำนวนและเจ้าของ Validator
- เลือก PoA แต่ไม่วิเคราะห์การสมรู้ร่วมคิดหรือการยึดบัญชี Validator
- วิเคราะห์ 51% Attack ทั้งที่ระบบไม่ได้ใช้ PoW หรือ PoS
- วิเคราะห์ความเสี่ยงที่ไม่สัมพันธ์กับ Consensus ที่เลือก
- Diagram กับ Pseudo-code ใช้ Actor หรือสถานะคนละชุด
- References ครบจำนวน แต่ไม่ได้ใช้สนับสนุนข้อกล่าวอ้างในเนื้อหา
- คัดลอก Whitepaper หรือกรณีศึกษาต่างประเทศโดยไม่ปรับกับบริบทบุรีรัมย์
- ทำ Presentation เป็นบทสรุปรายงานแบบอ่านสไลด์
- ให้ Technical Architect เป็นคนเดียวที่ตอบคำถามระบบได้
- กระจายงานไม่เท่าเทียมจน Peer Evaluation แตกต่างกันมาก

## สิ่งที่หัวข้อผ้าไหมต้องออกแบบให้ครบ

> ส่วนนี้เป็นข้อเสนอแนะเชิงออกแบบ ไม่ใช่ Requirement ที่อาจารย์กำหนดตายตัว

### 1. กำหนดสิ่งที่รับรองให้แคบและชัด

ควรกำหนดหน่วยรับรอง เช่น:

- ผ้าไหมหนึ่งผืน
- ผลิตภัณฑ์หนึ่งชิ้น
- ชุดการผลิตหนึ่ง Batch

ต้องระบุว่าใบรับรองยืนยันอะไร เช่น ผู้ทอ แหล่งผลิต วันที่ผลิต สหกรณ์ผู้ตรวจรับ และสถานะใบรับรอง ไม่ควรอ้างว่ายืนยันคุณภาพแท้ทั้งหมด หากยังไม่มีกระบวนการตรวจทางกายภาพรองรับ

### 2. Stakeholders

สามกลุ่มที่ระบุในเอกสารโดยตรง ได้แก่:

- ช่างทอ
- สหกรณ์
- ร้านค้า

กลุ่มเพิ่มเติมที่อาจพิจารณา แต่ต้องมีเหตุผลและหลักฐานรองรับ ได้แก่:

- ผู้บริโภค
- หน่วยงานหรือผู้ตรวจรับรอง

ไม่ควรเพิ่ม Actor จนเกิน 5 กลุ่ม

### 3. Trust Problem

ต้องพิสูจน์ว่าอย่างน้อยสองหรือสามองค์กรจำเป็นต้องใช้บันทึกร่วมกัน แต่ไม่ควรให้องค์กรเดียวแก้ไขประวัติทั้งหมดได้โดยลำพัง

ถ้าข้อเท็จจริงพบว่าสหกรณ์เป็นหน่วยงานกลางที่ทุกฝ่ายเชื่อถือและควบคุมข้อมูลทั้งหมดได้อย่างเหมาะสม ระบบ SQL พร้อม Audit Log อาจเพียงพอ ในกรณีนั้นต้องลดข้อกล่าวอ้างหรือทบทวนความจำเป็นของ Blockchain

### 4. ธุรกรรมหลัก

Scope ขั้นต่ำที่เหมาะสมอาจมี:

- ลงทะเบียนชิ้นผ้าและข้อมูลผู้ทอ
- ตรวจสอบและออกใบรับรองโดยสหกรณ์
- เปลี่ยนสถานะหรือบันทึกการส่งมอบให้ร้านค้า
- ตรวจสอบใบรับรองผ่าน QR Code

สำหรับแบบฟอร์มอนุมัติหัวข้อ ควรเลือกเพียง 2–3 Transaction หลักตามที่ภาคผนวก B ขอ

### 5. Blockchain Type และ Consensus

ทีมเลือก **Consortium Blockchain + Proof of Authority (PoA)** สำหรับ Blueprint และจำลองการทำงานภายในเว็บ โดยมีเหตุผลดังนี้:

- ผู้มีส่วนร่วมเป็นกลุ่มที่ระบุตัวตนและกำหนดสิทธิ์ได้
- หลายบทบาทต้องร่วมบันทึกและตรวจสอบประวัติ แต่ไม่เปิดให้บุคคลทั่วไปเขียนข้อมูล
- PoA เหมาะกับ Validator จำนวนน้อยที่ได้รับอนุญาตและไม่ต้องใช้เหรียญหรือการขุด
- เว็บจำลอง Validator Roles และการลงนาม Block; ไม่อ้างว่าเป็นเครือข่ายกระจายศูนย์จริง

Validator Roles ที่เสนอใน Blueprint คือ สหกรณ์ผ้าไหม หน่วยงานตรวจรับรองท้องถิ่น และตัวแทนเครือข่ายร้านค้า ชื่อองค์กรจริงยังต้องยืนยันด้วยหลักฐานก่อนใช้ในรายงาน

### 6. Data Design

ข้อมูลที่อาจอยู่ On-chain:

- Certificate ID
- Product/Batch ID
- Weaver Pseudonymous ID
- Cooperative/Issuer ID
- Timestamp
- สถานะใบรับรอง
- Hash ของหลักฐานหรือเอกสาร
- Transaction Signer
- Previous Hash และ Block Hash

ข้อมูลที่ควรพิจารณาเก็บ Off-chain:

- ชื่อและข้อมูลติดต่อเต็มของช่างทอ
- ภาพถ่ายความละเอียดสูง
- เอกสารรับรองฉบับเต็ม
- ข้อมูลส่วนบุคคลหรือข้อมูลที่ต้องแก้ไขหรือลบได้

### 7. Smart Contract Rules

อย่างน้อยต้องอธิบายกฎสำหรับ:

- ใครสร้างรายการผ้าได้
- ใครออกหรืออนุมัติใบรับรองได้
- ออกใบรับรองซ้ำได้หรือไม่
- แก้ข้อมูลเดิมอย่างไรโดยไม่ลบประวัติ
- เพิกถอนหรือระงับใบรับรองอย่างไร
- ร้านค้าเปลี่ยนสถานะได้ในเงื่อนไขใด
- ผู้บริโภคเห็นข้อมูลส่วนใด

### 8. Physical–Digital Link

ต้องยอมรับว่า Blockchain ป้องกันการแก้ประวัติบนระบบ แต่ไม่สามารถรับรองเองได้ว่าผ้าไหมที่ติด QR คือผืนเดียวกับที่ตรวจจริง จำเป็นต้องออกแบบกระบวนการ Onboarding การตรวจรับ และกลไกรับมือ QR ถูกคัดลอก

### 9. PDPA และ Ethics

ควรครอบคลุม:

- วัตถุประสงค์การเก็บข้อมูล
- ข้อมูลใดเป็นข้อมูลส่วนบุคคล
- ใครเข้าถึงข้อมูลใดได้
- การขอความยินยอมเมื่อจำเป็น
- การเพิกถอนความยินยอม
- การแก้ไขหรือลบข้อมูล Off-chain
- การใช้ Hash หรือ Pseudonymous Identifier บน Chain
- ความเสี่ยงที่ช่างทอรายย่อยเสียเปรียบหรือเข้าถึงเทคโนโลยีไม่ได้

### 10. Cost-Benefit และข้อจำกัด

ต้องเปรียบเทียบอย่างน้อยกับ Centralized SQL ในด้าน:

- ค่าโครงสร้างพื้นฐาน
- ค่า Validator และการบริหารสมาชิก
- การฝึกอบรม
- ความซับซ้อน
- ความเร็ว
- ความสามารถตรวจสอบย้อนหลัง
- การพึ่งพาองค์กรกลาง
- ความคุ้มค่าตามจำนวนผู้ใช้งานจริง

### 11. Limitations และ Future Work

ควรครอบคลุม:

- Technical Limitations
- Financial Limitations
- Regulatory Limitations
- ความเสี่ยงของ Consensus ที่เลือก
- Oracle/Garbage-in-garbage-out Problem
- QR Code Duplication
- การบริหาร Validator และสิทธิ์ของสมาชิก
- แนวทางพัฒนา Prototype หรือ Pilot ใน Phase ถัดไป

## ข้อสรุปด้าน Scope

Scope ที่เหมาะสมและตรงโจทย์มากที่สุดคือ:

> เว็บ Nuxt แบบ Full-stack พร้อม PostgreSQL และ Local Blockchain Simulation สำหรับออกใบรับรองและตรวจสอบประวัติของผ้าไหมหนึ่งชิ้นหรือหนึ่งชุดการผลิต ระหว่างช่างทอ สหกรณ์ และร้านค้า โดยเปิดให้ผู้บริโภคตรวจสอบข้อมูลที่เหมาะสม

ไม่ควรขยายเป็น Marketplace, Cryptocurrency, NFT, ระบบชำระเงิน หรือ Supply Chain ครบวงจรในโครงงานเดียว เว้นแต่มี Requirement เพิ่มเติมและได้รับการอนุมัติจากอาจารย์
